# 编码工作流（coding-workflow）三阶段规程

每个任务 = 工作区 `Agents/` 下的一个文件夹；一个任务的生命周期被强制切成三个**依次进行**的阶段：

| 阶段 | 名称 | 输入 | 产出 |
|---|---|---|---|
| S1 | 需求 | 用户原始需求 + 澄清问答 | `S1_DEMAND.md` |
| S2 | 设计 | `S1_DEMAND.md` + 工作区代码分析（可联网检索参考） | `S2_DESIGN.md` |
| S3 | 实施 | `S1_DEMAND.md` + `S2_DESIGN.md` | 代码变更 + `S3_IMPLEMENT.md` |

- 阶段顺序不可跳过、阶段指针不可回退（见第 6、7 节）。
- 每个任务的阶段状态记录在 `PROGRESS.md`，它是判断"当前处于第几阶段"的唯一依据。
- 所有阶段文档：**不存在则新建，存在则原位修改**。不写副本、不写 `-v2`、不写到任务文件夹之外。

## 1. 任务定位与会话初始化

每个新会话在尚未定位任务时，第一步永远是任务定位。同一会话只做一次，之后不再重复询问，除非用户要求切换任务。

1. 检查工作区根目录的 `Agents/` 是否存在，列出其下的任务子文件夹（子文件夹即任务；忽略文件和明显无关的目录）。
2. 按情形处理：
   - **`Agents/` 不存在，或存在但没有任何任务文件夹** → 用 `ask_user_question` 发起提问框，只问一个问题让用户输入任务名称。收到答复后创建 `Agents/{任务名称}/`，写入初始 `PROGRESS.md`，进入 S1。
   - **已有任务文件夹** → 用 `ask_user_question` 发起提问框：每个任务一个选项（label 用文件夹名，description 简要说明该任务当前阶段与最近进展），并在选项最后固定附一项 **「新建任务…」**，让用户可以不选老任务直接新建。
     - 用户选择已有任务 → 读它的 `PROGRESS.md`，按「当前阶段」恢复工作。
     - 用户选择「新建任务…」→ 再发一个提问框请用户输入任务名称（若提问框允许在选项之外直接输入，优先让用户在同一步完成），然后创建文件夹并进入 S1。
3. 任务命名：任务名称即文件夹名，建议中文或英文短名；若用户给的名字含 `/ \ : * ? " < > |` 或首尾空格等不安全字符，做必要清理并告知用户清理结果。
4. 定位任务后，向用户用一两句话确认：进入了哪个任务、当前处于哪个阶段、接下来做什么。

## 2. PROGRESS.md — 阶段状态的唯一事实来源

新建任务时写入初始内容；之后**每完成一段有意义的推进就更新**（宁可多更，不可失真）。记录保持简要，不写成流水账。

````markdown
# PROGRESS — {任务名称}

- 当前阶段: S1需求        <!-- 取值固定: S1需求 / S2设计 / S3实施 / 已完成；只前进，不后退 -->
- 最近更新: YYYY-MM-DD HH:mm

## 当前阶段进展
- （本阶段已完成的动作、已产出的文件、当前卡点）

## 阶段历史
- S1需求: 进行中 ｜ 已完成（YYYY-MM-DD，产出 S1_DEMAND.md）
- S2设计: 未开始 ｜ 进行中 ｜ 已完成（YYYY-MM-DD，产出 S2_DESIGN.md）
- S3实施: 未开始 ｜ 进行中 ｜ 已完成（YYYY-MM-DD，产出 S3_IMPLEMENT.md）

## 待办与未决问题
- （等待用户答复的问题、跨阶段变更的回溯记录等）
````

**恢复规则**：定位到已有任务后先读 `PROGRESS.md`。「当前阶段」字段直接决定从哪里继续。若该文件缺失或损坏，按阶段文件存在性推断——有 `S3_IMPLEMENT.md` 视为 S3；只有 `S2_DESIGN.md` 视为 S3 或 S2（结合内容判断）；只有 `S1_DEMAND.md` 视为 S2 或 S1——推断后先重建 `PROGRESS.md` 并向用户说明，再继续。

## 3. S1 需求

**目标**：把用户口述的想法变成一份双方确认过、可据以设计的 `S1_DEMAND.md`。

动作序列：

1. 接收用户需求描述，开始需求层面的分析。**本阶段不擅自分析代码**：不读取、不检索、不推断工作区的代码文件（除非用户明确要求）；需要代码事实才能回答的疑问，一律记入 `S1_DEMAND.md` 的「待 S2 确认」清单，留到 S2 处理。本阶段可以读的只有任务自身的阶段文档（例如恢复上下文时读 `PROGRESS.md`）。
2. 分析原始需求，找出三类必须澄清的问题：
   - **不完善**：目标模糊、范围不明、验收标准缺失、影响面未知；
   - **冲突**：需求之间、需求与现状或约束之间的矛盾；
   - **歧义**：同一描述存在多种合理解读。
3. 用 `ask_user_question` 向用户追问。纪律：
   - 能给选项就给选项（附上你的理解和推荐项），真正开放的问题才用输入框；
   - 每个问题都带上你的当前理解，让用户确认或纠正，而不是让用户凭空描述；
   - 得到答复后复述结论；出现新的衍生疑问才追问下一轮，一般不超过两轮；
   - 两轮后仍未决的点，把你的处理假设显式写进文档第 6 节，供用户复核；
   - 只问需求本身，不问代码细节（代码位置是 S2 的事）；
   - 不擅自分析代码：即使想确认现状是怎么实现的，也不去翻代码——把疑问记入「待 S2 确认」，或请用户直接补充说明。
4. 汇总原始需求与全部澄清结论，写 `S1_DEMAND.md`（模板见下）。
5. 走阶段门槛（第 6 节）。

`S1_DEMAND.md` 模板（小需求可精简小节，但「澄清记录」和「验收标准」不可省）：

````markdown
# S1 需求文档 — {任务名称}

- 状态: 已确认（YYYY-MM-DD）
- 来源: 用户原始需求 + 澄清问答

## 1. 背景与问题
## 2. 目标与范围
<!-- 做什么；同样重要的是：明确不做什么 -->
## 3. 需求明细
<!-- 每条含：描述 / 优先级（必须·应该·可以）/ 验收要点 -->
## 4. 约束与非功能要求
## 5. 边界与排除项
## 6. 澄清记录
<!-- 原始需求摘要；每轮问答：问题 → 用户答复 → 采纳结论；未决项的处理假设 -->
## 7. 验收标准
<!-- 可核对的标准清单；S2 的测试计划与 S3 的自测都要回指这里 -->
## 8. 待 S2 确认
<!-- 需要代码事实才能回答的疑问清单；S1 不擅自翻代码，留到 S2 逐一核实 -->
````

## 4. S2 设计

**目标**：把 S1 的"做什么"落成"怎么改"——一份含现状分析、详细设计与分步实施计划的 `S2_DESIGN.md`。

动作序列：

1. 重读 `S1_DEMAND.md`，逐条对齐需求与验收标准。
2. 分析工作区代码：用 glob / grep / read 梳理相关模块与文件职责、数据表、接口、关键函数与调用关系；需求涉及不熟悉的外部技术或框架用法时，用 `web_search` / `web_fetch` 检索关联知识参考，并把关键结论与来源记入设计文档。
3. **代码位置追问（强制）**：若本次是"在原有代码基础上变更"的需求，且用户在 S1 及澄清过程中**没有**给出涉及的代码位置（文件名、数据库表名、代码关键字），必须用 `ask_user_question` 向用户追问：
   - 每次提问框只问**一个**问题；有多个要问的，分开来一次一次问，前一个得到答复后再问下一个；
   - 先做代码分析、带着自己的推测去问（例如："改动是否发生在 X 模块？若不是，请给出相关文件名/表名/代码关键字"），用输入框让用户填写；
   - 问到的位置信息全部写进设计文档第 2 节；
   - 若分析确认改动只涉及全新代码、不触碰存量代码，可不追问，但要在文档中写明这一判断及其依据。
4. 写 `S2_DESIGN.md`（模板见下）：现状 → 影响面 → 详细设计 → 分步实施计划（每步含改动文件、具体内容、自验证方式）→ 风险与回退 → 测试计划（逐条回指 S1 验收标准）。
5. 走阶段门槛（第 6 节）。

`S2_DESIGN.md` 模板：

````markdown
# S2 设计文档 — {任务名称}

- 状态: 已确认（YYYY-MM-DD）
- 依据: S1_DEMAND.md（YYYY-MM-DD 版本）

## 1. 需求回顾
<!-- 引用 S1 的关键条目与验收标准 -->
## 2. 现状代码分析
<!-- 相关文件清单：路径 + 职责 + 与本需求的关系；数据表 / 接口 / 关键函数现状；用户提供的代码位置信息 -->
## 3. 变更影响面
<!-- 直接改动的文件与模块；受影响的调用方、数据、兼容性 -->
## 4. 详细设计
<!-- 方案：新增/修改什么；数据结构与接口变更；关键流程（伪代码或时序说明） -->
## 5. 实施计划
<!-- 分步列表：每步 = 改动文件 + 具体内容 + 自验证方式；步骤尽量可独立验证 -->
## 6. 风险与回退
## 7. 测试计划
<!-- 对照 S1 验收标准，逐条给出验证方法 -->
````

## 5. S3 实施

**目标**：严格按 `S2_DESIGN.md` 的实施计划编码，并留下可追溯的变更记录。

动作序列：

1. 重读 `S1_DEMAND.md` 与 `S2_DESIGN.md`；用 `todo_write` 把 S2 实施计划转成任务清单，逐步执行。
2. 每完成一步：执行该步的自验证；随即更新 `S3_IMPLEMENT.md` 的进度表与变更清单（不要攒到最后补写）。
3. 实施中发现设计有问题：小偏差直接实施并记入「与设计的偏差」；实质性方案变更，先向用户说明并确认，再同步修订 `S2_DESIGN.md`（必要时连带修订 `S1_DEMAND.md`，见第 7 节），然后继续。
4. 全部步骤完成后：对照 S1 验收标准做整体自测；补全 `S3_IMPLEMENT.md`；走阶段门槛——S3 的门槛就是交付验收，用户确认后把 `PROGRESS.md` 的当前阶段记为「已完成」。

`S3_IMPLEMENT.md` 模板：

````markdown
# S3 实施记录 — {任务名称}

- 状态: 进行中 ｜ 已完成（YYYY-MM-DD）

## 实施进度（对照 S2 实施计划）
| 步骤 | 计划内容 | 状态 | 备注/偏差 |
|---|---|---|---|

## 变更清单
### 新增文件
- `路径` — 用途
### 修改文件
- `路径` — 变更点摘要（到函数/类/行为级别）

## 关键实现说明
## 与设计的偏差
<!-- 没有则写"无" -->
## 自测与验证记录
````

## 6. 阶段门槛（Gate）

当你觉得可以转阶段时，**第一动作是先询问用户，而不是开始下一阶段的工作**：必须用 `ask_user_question` 发起门槛确认，由用户决定是否推进；未经用户明确确认，不得自行推进，也不得提前做下一阶段的任何准备工作（读代码、写文档都不行）。话术：

> **question**: S{N} {阶段名}阶段已基本完成（{产出文件} 已写入 Agents/{任务名称}/）。是否进入下一阶段？
> **options**: ① 进入 S{N+1} {下一阶段名}（推荐）② 继续调整 S{N}

- 用户选择**继续调整** → 留在当前阶段，按用户意见修改；改完后**再次**发起门槛确认。
- 用户选择**进入下一阶段** → 更新 `PROGRESS.md`（当前阶段前移，上一阶段记入阶段历史），开始下一阶段。**此后阶段指针不可回退**——即使后续发现先前阶段有遗漏，也只能按第 7 节的变更流程修订文档，而不是把状态退回去。
- S1 → S2、S2 → S3、S3 → 交付验收，三处门槛缺一不可。
- 需求很小时走"轻量阶段"：文档按需求规模伸缩，但阶段顺序、产出文件与门槛确认一项都不能省。

## 7. 跨阶段变更（不回退指针的回溯修订）

用户在任何阶段都可以要求变更先前阶段的内容文件（例如 S3 期间需求变了）。流程：

1. 先按 S1 的追问纪律澄清变更内容，明确"改什么、为什么改"。
2. 更新被要求变更的阶段文档（如 `S1_DEMAND.md`），并在其文末追加一条变更记录（日期 + 变更说明）。
3. **连带评估**：检查后续阶段文档是否受影响——
   - 改了 S1 → 评估并同步修订 `S2_DESIGN.md`（需求回顾、设计、实施计划、测试计划）；
   - 改了 S2 → 评估 S3 已实施部分，向用户说明既有代码改动何去何从（保留 / 调整 / 回退）。
4. 更新 `PROGRESS.md`：「当前阶段」保持不变，把这次回溯修订记入「待办与未决问题」或阶段历史。
5. 继续当前阶段的工作（例如 S3 中按新文档继续编码）。

> 一句话：**回退的是文档内容，不是阶段位置。**
